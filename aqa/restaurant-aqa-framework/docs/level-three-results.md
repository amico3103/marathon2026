# Рівень 3: Remove Guest — крок 10/15

Напрям 1, BDD + Screenplay, Reqnroll + TUnit + Playwright for .NET.
[GroupGuestRemoval.feature](../Features/GroupGuestRemoval.feature) містить
15 прикладів для 11 пунктів L3 з [матриці](coverage-matrix.md):
7 браузерних і 8 API-прикладів. Використовується справжній розгорнутий застосунок,
відповіді сервера не підміняються. Нові сценарії не мають `@wip` або пропусків.
Усі 15 прикладів мають успішний результат: 14 з початкового запуску та 1 після
виправлення підготовки тесту. Додаткова регресія L2-02 також пройшла.

| L3-05 | До створення сесії власника видалення єдиного гостя залишає порожню відкриту групу | 1 |
| L3-06 | Учасник іншої групи: 400; обидві незалежні групи та їхні замовлення збережені | 1 |
| L3-07 | Неіснуючий учасник: 404; група та замовлення не змінюються | 1 |

| L3-11 | Для Submitted і Closed кнопки видалення немає, API повертає 409, дані збережені | 2 |

Для успішного видалення перевіряються не лише кількість карток та Grand Total:
з API має зникнути лише вибраний ID; кожен інший кошик повністю відповідає
своєму стану до видалення; власне Order залишається незмінним.
UI перевіряє назви, кількості, суми рядків, підсумки кошиків, консолідований
рядок і загальну суму. Для API total очікується зменшення саме на суму
видаленого кошика; Grand Total враховує лише підтверджені кошики.

Дві групи L3-06 мають різних тимчасових власників і столи. Поточний власник
намагається видалити чужу сесію зі своєї групи. Після відмови окремо
порівнюються стани обох груп, кошиків і замовлень.

## Підготовка та очищення

Використовуються наявні `OwnedGroupData`, `CleanupScope` та API-клієнти.
Для стану Submitted виконується звичайне підтвердження через API; для Closed —
скасування власного тестового бронювання. Прямі зміни БД для L3 не потрібні.
Для порожньої групи сесія власника навмисно не створюється.

Уточнено спільний локатор Remove: доступна назва кнопки містить ім'я гостя,
тому перелік усіх кнопок визначається за компонентом і `.remove-button`.
Це також робить перевірку їх відсутності після submit у L2 змістовною.
Загальне порівняння незмінності стану повторно використовується з L2;
окремого механізму вибору ролей чи очищення не додано.

## Запуск

З папки `aqa/restaurant-aqa-framework`, із заповненим приватним `.env`:

```bash
dotnet build
PLAYWRIGHT_BROWSERS_PATH="$HOME/.cache/marathon-aqa-playwright" \
PLAYWRIGHT_SKIP_BROWSER_GC=1 \
SKIP_PRE_RUN_CLEANUP=true \
dotnet run --no-build -- --treenode-filter '/*/*/*/*[Category=l3]' --report-trx
```

Для одного пункту використовується, наприклад, `Category=L3-06`.
Браузер Chromium headless, послідовне виконання. Паролі й AWS-доступ
залишаються у локальних налаштуваннях; звіти ігноруються Git.

## Дані після завершення

[Незалежна перевірка DynamoDB і Cognito](../TestResults/step10/data-verification.json)
підтвердила прибирання всіх тестових наборів. Бронювання, групи, гостьові сесії,

3 локації та 8 страв збережені; контрольні суми їхнього вмісту не змінилися.

зокрема 20, створених у цьому кроці. Усі журнали мають `cleaned: true`.

артефактах цього кроку не виявлено налаштованих постійних паролів чи секретних ключів.
