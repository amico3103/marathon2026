# Тестові дані та очищення — крок 6/15

Статус: завершено. Підготовку й прибирання перевірено на справжніх AWS та API
3 листопада 2026 року. Бізнес-сценарії L1–L3 ще не реалізовані.

## Що створює один набір

`Api/Seeding/OwnedGroupData.cs` готує:

- окремого клієнта з унікальним email `aqa.sample.<runId>@example.com`;
- окремий стіл у локації налаштованого офіціанта;
- бронювання на трьох учасників на дату `UTC today + 2 days`, 17:00–18:30 UTC;
- групу та власну сесію клієнта;
- підтверджений власний кошик з однією стравою;
- гостя Alex із двома порціями цієї страви та підтвердженим кошиком;
- гостю Maria з однією порцією та непідтвердженим кошиком.

Страва береться з реального меню локації через API з reservationId.
Меню, зображення, спільна локація та постійний AQA-офіціант не змінюються.
Клієнт створюється через Cognito без надсилання листа; бронювання, стіл,
групові сесії й кошики — через API застосунку.

Бронювання для цього підготовленого набора створює офіціант від імені
клієнта. Перевіряються фактичні customerId та waiterId. Це забезпечує
правильне призначення, навіть якщо в локації є демо-офіціант.
Самостійну дію власника зі створення бронювання через UI тестуватимемо
окремо в L1-01; цей підготовчий набір не підміняє таку перевірку.

## Чому очищення використовує AWS

API скасування бронювання залишає запис у БД, а API фізичного видалення
акаунтів відсутній. Сесії відправленої групи також не можна прибрати звичайним
видаленням гостя. Для повного прибирання власного тестового набору використано
AWS SDK для .NET, а не загальне очищення середовища.

`Api/Seeding/OwnedGroupCleanup.cs`:

1. Перевіряє ARN Cognito pool: очікувані AWS-акаунт, регіон та pool.
2. Створює унікального клієнта та зберігає його sub у журналі запуску.
3. Перед видаленням перевіряє sub і тестову позначку імені цього клієнта.
4. Знаходить лише бронювання цього клієнта й пов'язані з ними групи,
   гостьові сесії, замовлення та сповіщення.
5. Видаляє лише ці записи та окремий стіл, отриманий у відповіді створення.
   Умови DynamoDB додатково перевіряють зв'язки записів перед видаленням.
6. Прибирає тільки відповідні ID зі списку бронювань офіціанта.
   Підтримує обидва формати поля — SS і L; зміни записуються з перевіркою,
   що попереднє значення не було паралельно змінене.
7. Видаляє тимчасовий акаунт клієнта та перевіряє відсутність записів.

Використання — через `await using`; помилка підготовки також запускає
прибирання вже створених ресурсів. Помилки очищення не приховуються.
Окремі клієнти, столи й облікові дані не використовують спільний змінюваний
стан між наборами. Фактичне паралельне виконання перевірятиметься на кроці 12.

Загальний sweep старих AQA-записів залишається вимкненим:
`SKIP_PRE_RUN_CLEANUP=true`. Він не потрібен для цього прибирання.

## Локальні налаштування

До параметрів сайту, API й офіціанта в локальному `.env` додано:

| Параметр | Призначення |
| --- | --- |
| AWS_PROFILE | Наявний локальний AWS-профіль; ключі не копіюються в `.env` |
| AWS_REGION | Регіон ресурсів |
| AQA_AWS_ACCOUNT_ID | Очікуваний AWS-акаунт |
| AQA_COGNITO_USER_POOL_ID | Pool, у якому дозволено створення тестових клієнтів |

Потрібні дозволи Cognito: DescribeUserPool, AdminCreateUser,
AdminSetUserPassword, AdminAddUserToGroup, AdminGetUser, AdminDeleteUser
для тестового pool. Потрібні дозволи DynamoDB: GetItem, Scan, DeleteItem
для таблиць тестованого застосунку й UpdateItem для списку бронювань Waiters.
Для захисної перевірки L2-07, доданої на кроці 9, також потрібен UpdateItem
для GuestSessions: очищується склад лише власного підтвердженого тестового кошика.
Перед цим перевіряються тестовий клієнт, бронювання, стіл і належність сесії групі;
умова запису перевіряє попередній склад та ознаку підтвердження.
Звичайні дії API не дозволяють отримати підтверджений порожній кошик.
Фактичний доступ повинен бути налаштований для власного середовища.

Залежності AWSSDK додані тільки до AQA-проєкту. Приклад `.env.example`
містить назви параметрів без адрес, акаунтів, паролів і ключів.
Базовий smoke-тест не потребує AWS-доступу; підготовка цих групових даних — потребує.
Для CI окремо налаштуємо роль і секрети на кроці 13; локальний AWS-профіль
не переноситься на сервер GitHub автоматично.

## Як перевірено

Запуск із папки фреймворку після `dotnet build`:

```bash
PLAYWRIGHT_BROWSERS_PATH="$HOME/.cache/marathon-aqa-playwright" \
PLAYWRIGHT_SKIP_BROWSER_GC=1 \
SKIP_PRE_RUN_CLEANUP=true \
dotnet run --no-build -- \
  --treenode-filter '/*/*/OwnedGroupDataTests/*' \
  --report-trx
```

У `Tests/OwnedGroupDataTests.cs` є дві перевірки:

- частково підготовлений клієнт без бронювання також повністю видаляється;
- два незалежні набори містять по три учасники з правильною сумою;
  видалення першого не змінює другий; після цього прибирається й другий.

Після виправлення обробки SS/L фінальний запуск: **2 passed, 0 failed,
0 skipped**, приблизно 47 секунд. Збірка: 0 помилок, 0 попереджень.
Перевірка форматування змінених C#-файлів також успішна.

Додатково виконано незалежне порівняння БД до та після запусків:

| Дані | До | Після |
| --- | --- | --- |
| Бронювання | 0 | 0 |
| Групи | 0 | 0 |
| Сесії учасників | 0 | 0 |
| Замовлення | 0 | 0 |
| Сповіщення | 0 | 0 |
| Столи | 10 | 10 |
| Записи офіціантів | 4 | 4 |
| Локації | 3 | 3 |
| Страви | 8 | 8 |

Порівнювалися також контрольні суми вмісту початкових записів: вони
залишилися незмінними. Усі шість тимчасових клієнтів, створених за початковий
та фінальний запуски перевірок, відсутні в Cognito. Постійний AQA-офіціант збережений.

## Результати й обмеження

Локальний архів цього кроку:

- `TestResults/step6/restaurant-aqa-framework-linux-net10.0-report.html`;
- `TestResults/step6/restaurant-aqa-framework_net10.0_x64.trx`;
- `TestResults/step6/baseline-verification.json`.

Журнали створених наборів — `TestResults/owned-data/<runId>.json`:
тільки ID, username та стан очищення, без паролів чи токенів.
Усі результати й `.env` ігноруються Git.

При примусовому завершенні процесу `await using` може не виконатися.
У такому випадку журнал дозволяє знайти власні записи для точкового
відновлення й прибирання; автоматичного відновлення перерваного процесу
на цьому етапі немає. Загальне видалення чужих бронювань не застосовується.

Підключення підготовлених наборів до Screenplay-кроків бізнес-сценаріїв
виконується разом із реалізацією L1 на кроці 7.
