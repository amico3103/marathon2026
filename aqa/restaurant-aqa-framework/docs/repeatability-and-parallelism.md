# Повторюваність та паралельне виконання — крок 12/15

Підсумок: **45/45 послідовно**, **44/45 та 43/45 паралельно**.
Одночасність 2 та незалежність тестових даних підтверджені. Безпомилковий
повний паралельний прогін на цьому середовищі не отримано через транспортні збої.

Усі чотири feature домашньої роботи мають спільний тег `@group-preorder`.
Він вибирає 45 прикладів: L1 — 14, L2 — 15, L3 — 15 та E2E — 1.
Це власні перевірки групового преордера; початкові сценарії фреймворку
з іншими вимогами до даних або `@wip` до цього набору не входять.

## Що перевіряється

Повний набір виконується двічі на незмінній збірці:

1. `MAX_PARALLEL_TESTS=1`: сценарії виконуються послідовно.
2. `MAX_PARALLEL_TESTS=2`: два сценарії можуть виконуватися одночасно.

Для обох запусків очікуються ті самі 45 прикладів без помилок і пропусків.
Кожен режим виконується одним процесом; наступний починається після збереження
звітів та перевірки очищення попереднього. Під час тестів загальний sweep
вимкнений: кожен сценарій прибирає лише власні записи.

Паралельність керується наявним `Configuration/ParallelismConfig.cs` через
TUnit ParallelLimiter. Змінна процесу має пріоритет над `.env`.
Локальне значення `.env` залишається 1; режим 2 задається командою запуску.

## Команди

З папки `aqa/restaurant-aqa-framework`, після заповнення `.env` і встановлення браузерів:

```bash
dotnet build
dotnet run --no-build -- --list-tests --treenode-filter '/*/*/*/*[Category=group-preorder]'

export PLAYWRIGHT_BROWSERS_PATH="$HOME/.cache/marathon-aqa-playwright"
export PLAYWRIGHT_SKIP_BROWSER_GC=1
export SKIP_PRE_RUN_CLEANUP=true

MAX_PARALLEL_TESTS=1 dotnet run --no-build -- --treenode-filter '/*/*/*/*[Category=group-preorder]' --report-trx
```

Після збереження результатів першого запуску:

```bash
MAX_PARALLEL_TESTS=2 dotnet run --no-build -- --treenode-filter '/*/*/*/*[Category=group-preorder]' --report-trx --output Detailed --progress off
```

Кореневі HTML/TRX/Reqnroll-звіти перезаписуються наступним запуском.
Контрольні результати цього кроку архівуються окремо в `TestResults/step12/`.
`--output Detailed --progress off` у другому запуску змінює лише виведення
журналу: кожен результат видно окремим блоком. Вибір тестів і збірка однакові.

## Перша паралельна спроба

Результат: **44 passed, 1 failed, 0 skipped**, **9 хв 23 с**.
L3-02 завершився `net::ERR_NAME_NOT_RESOLVED` при переході на сторінку входу,
до виконання видалення гостя. Помилка навігації збережена у звіті й trace.
Підготовлені для цього тесту дані також прибрані.

Подальші незалежні перевірки системного DNS та HTTPS пройшли: адреса CloudFront
визначалася, `/login` повертав HTTP 200. Інші UI-сценарії продовжували проходити.
Причину окремого DNS-збою не встановлено; налаштування мережі, застосунок і тести
через нього не змінювалися. Автоматичного повтору сценарію не було.

Перший невдалий запуск зберігається окремо:

- [HTML TUnit](../TestResults/step12/parallel-initial/restaurant-aqa-framework-linux-net10.0-report.html);
- [TRX](../TestResults/step12/parallel-initial/restaurant-aqa-framework_net10.0_x64.trx);
- [Перевірка DNS і HTTPS](../TestResults/step12/parallel-initial/network-check.json);
- `TestResults/step12/parallel-initial/traces/` містить trace невдалого L3-02.

Для перевірки всього паралельного набору після цього збою призначено новий
повний запуск тих самих 45 прикладів на тій самій збірці. Початкова невдача
залишається частиною результатів; повтор не підміняє її звіт.

Фактична максимальна одночасність у TRX — **2**. Після цієї спроби всі
49 наборів прибрані автоматично, початкові записи не змінилися, усі 170
тимчасових акаунтів із накопичених журналів відсутні в Cognito.
[Звірка після першої паралельної спроби](../TestResults/step12/parallel-initial/data-verification.json).

## Повторний паралельний запуск

застосунок і виконувані джерела тестів не змінювалися. Нові повні повтори

## Очищення після мережевої помилки

У повторі створено 48 наборів: мережевий збій стався до створення додаткового
чужого клієнта L2-12. З них 47 прибрані автоматично. Один набір L2-11 залишився
через помилку з'єднання з Cognito під час cleanup.

Після завершення процесу його прибрано точково за журналом. Перед видаленням
перевірено AWS-акаунт і pool, sub та тестову позначку клієнта, належність
бронювання, столу, групи й дочірніх записів. Видалено лише ці записи та їхнє
посилання в офіціанта. Копія початкового журналу й запис відновлення збережені
в `TestResults/step12/recovery/`; `cleanupRecovery` у журналі явно позначає
операційне відновлення. Невдалий результат тесту при цьому не змінювався.

[Незалежна звірка після відновлення](../TestResults/step12/parallel/data-verification.json)
підтвердила відсутність тестових бронювань, груп, сесій, замовлень і сповіщень.
Початкові 10 столів, 4 офіціанти, 3 локації та 8 страв збережені; контрольні
суми їхнього вмісту не змінилися. Усі 218 тимчасових акаунтів із накопичених
журналів відсутні в Cognito, зокрема 146, створені за три запуски цього кроку.

Порівняння звітів підтвердило однакові 45 прикладів, незмінність виконуваних
джерел та відсутність повторно використаних ID клієнтів, столів, бронювань
і груп між трьома запусками. Усі 146 наборів прибрані: 145 автоматично,
один — точковим операційним відновленням, описаним вище.

## Практичний висновок

Поточний підтверджений режим для обов'язкового запуску — `MAX_PARALLEL_TESTS=1`:
45 прикладів пройшли разом без помилок. Режим 2 виконується паралельно та
не змішує ID наборів, але повна стабільність на цій мережі ще не підтверджена.
Його слід повторно перевірити на CI-середовищі; мережеві помилки залишаються
відкритим обмеженням, а не позначаються успішними тестами.

Невдалі HTTP-логи можуть містити тимчасові Bearer-токени Playwright.
Архіви залишаються локальними; перед публікацією CI-артефактів на кроці 13
потрібне вилучення таких значень зі звітів і перевірка traces.

## Докази

- Discovery має знайти рівно 45 прикладів за спільним тегом.
- Для кожного режиму зберігаються HTML TUnit, TRX, BDD-звіт, лог та traces.
- Час початку й завершення кожного прикладу в TRX використовується для
  підрахунку фактичного одночасного виконання; одного значення змінної недостатньо.
- Контрольні суми C#, feature, csproj та Reqnroll-конфігурації фіксують
  незмінність виконуваних джерел між запусками.
- Порівнюються списки прикладів, відсутність повторно використаних ID наборів,
  клієнтів, столів, бронювань і груп, а також стан `cleaned` усіх журналів.
- Після кожного запуску окремо читаються DynamoDB і Cognito: власні тестові
  записи прибрані, початкові записи збережені.

Архіви можуть містити тимчасові токени браузерних сесій. Вони локальні
та ігноруються Git; публікація CI-артефактів налаштовується окремо на кроці 13.

Ця перевірка стосується одночасного виконання двох сценаріїв на поточному
середовищі, а не навантажувального тестування або гарантії для більшої паралельності.
GitHub Actions та фінальна інструкція перевіряючому — наступні кроки 13–15.
