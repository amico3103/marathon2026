# Рівень 1: реалізація — крок 7/15

Цей документ фіксує результат кроку 7. Повний запуск уже виконано на кроці 8:
**14 passed, 0 failed, 0 skipped** — див. [підсумковий звіт](level-one-results.md).

Реалізовано перегляд учасників групового преордера на справжньому сайті та API.
[GroupParticipants.feature](../Features/GroupParticipants.feature) містить 14
тестових прикладів для всіх 11 пунктів L1 з [матриці](coverage-matrix.md).
Окремі приклади потрібні для різних ролей і перевірок відсутньої групи через UI/API.
Моків, `@wip` або пропусків у новому feature немає.

## Що перевіряють тести

- L1-01: власник бронює через браузер, отримує запрошення; гість у незалежному
  браузерному контексті приєднується й додає страву; власник бачить його кошик.
- L1-02: правильні страви, кількості та підсумки різних учасників; API total.
- L1-03–04: власник бачить зміну кількості та підтвердження гостя після фонової
  синхронізації без перезавантаження сторінки. Для кількості також перевіряється API total.
- L1-05–08: непідтверджений кошик, гість без страв, група без сесій та лише власник.
- L1-09–10: доступ іншого клієнта, офіціанта, гостя та користувача без токена.
- L1-11: відсутня група через API та зрозуміле повідомлення з повторною спробою у UI.

Для інших сценаріїв стан готується через API та [ізольовані набори](owned-test-data.md).
Локатори знаходяться в `Ui/`, дії — у Screenplay Tasks, читання результатів —
у Questions, а Gherkin-кроки зв'язують ці частини. Очікування прив'язані до
видимого стану, а не до фіксованих пауз.

Очищення підключене до завершення кожного сценарію. Навіть якщо одна операція
прибирання завершується помилкою, інші виконуються, а помилка залишається видимою.
Постійні облікові дані офіціанта використовуються в окремому API-контексті без trace.
Гостьові браузерні контексти мають окремі traces; вони можуть містити тимчасові
токени, тому результати локальні та ігноруються Git.

## Як запускати

З папки `aqa/restaurant-aqa-framework`, із заповненим локальним `.env`
та встановленим Playwright Chromium:

```bash
dotnet build
dotnet run --no-build -- --list-tests --treenode-filter '/*/*/*/*[Category=l1]'
dotnet run --no-build -- --treenode-filter '/*/*/*/*[Category=L1-03]' --report-trx
```

У поточному середовищі браузери встановлені в окремий кеш; перед запуском:

```bash
export PLAYWRIGHT_BROWSERS_PATH="$HOME/.cache/marathon-aqa-playwright"
export PLAYWRIGHT_SKIP_BROWSER_GC=1
export SKIP_PRE_RUN_CLEANUP=true
```

Повний запуск, запланований на крок 8:

```bash
dotnet run --no-build -- --treenode-filter '/*/*/*/*[Category=l1]' --report-trx
```

Кореневі результати `TestResults/` перезаписуються наступним запуском:
потрібні звіти слід копіювати в окрему папку. Локальний AWS-профіль потрібен
для підготовки та прибирання даних; доступ GitHub CI налаштовуватиметься на кроці 13.
