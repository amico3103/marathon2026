# Наскрізний сценарій групового замовлення — крок 11/15

Напрям 1, BDD + Screenplay, Reqnroll + TUnit + Playwright for .NET.
[GroupPreOrderJourney.feature](../Features/GroupPreOrderJourney.feature) реалізує
E2E-01 з [матриці покриття](coverage-matrix.md) одним сценарієм на справжньому
розгорнутому Green & Tasty. Відповіді API не підміняються.
Контрольний запуск 3 листопада 2026 року: **1 passed, 0 failed, 0 skipped**,
**1 хв 40 с**, із першої спроби.

## Що відбувається

1. Готується окремий клієнт, стіл, бронювання на трьох і підтверджена порція
   власника. Це передумови через API; бронювання призначене тестовому офіціанту.
2. Alex в окремому браузерному контексті переходить за запрошенням, додає
   таку ж страву, як у власника, збільшує кількість до двох і підтверджує кошик.
3. Maria в іншому браузерному контексті переходить за тим самим запрошенням,
   додає одну порцію іншої страви та підтверджує свій кошик.
4. Власник входить через UI й бачить три підтверджені кошики. Перевіряються
   назви, кількості, суми рядків і кошиків, API total та Grand Total.
5. Власник видаляє Maria через діалог. Зникає лише її ID і картка;
   кошики власника й Alex збережені. Залишаються три порції першої страви,
   суми зменшуються саме на вартість порції Maria.
6. Власник підтверджує консолідоване замовлення через UI: Group — Submitted,
   Order — SubmittedByCustomer; екран без редагування.
7. Призначений офіціант у четвертому браузерному контексті відкриває потрібне
   бронювання через свої фільтри й бачить один рядок із трьома порціями.
8. Унікальної страви Maria немає ні в Order через API, ні на сторінці офіціанта.

Страви та ціни беруться з реального меню локації цього бронювання.
Видалена страва обов'язково має інший ID та назву, тому її відсутність можна
перевірити однозначно. Результат не маскується однаковими назвами страв.
Обидва гостьові кошики створюються й підтверджуються через UI; фікстура
не створює їх замість гостей.

## Реалізація та перевірка спільних дій

Повторно використовуються наявні page objects, Tasks, Questions і перевірки
L1–L3. Дії гостя отримали ім'я свого браузерного контексту; попереднє значення
`guest` залишилося типовим. Видалення додатково вміє знайти гостя, створеного
через UI, за ім'ям у власній групі й отримати його справжній ID з API.
Нові окремі механізми авторизації, очищення або підміни даних не додавалися.

## Запуск

З папки `aqa/restaurant-aqa-framework`, після налаштування `.env` і браузерів:

```bash
dotnet build
PLAYWRIGHT_BROWSERS_PATH="$HOME/.cache/marathon-aqa-playwright" \
PLAYWRIGHT_SKIP_BROWSER_GC=1 \
SKIP_PRE_RUN_CLEANUP=true \
dotnet run --no-build -- --treenode-filter '/*/*/*/*[Category=E2E-01]' --report-trx
```

Сценарій позначено `@e2e`, `@ui`, `@E2E-01` та `@trace-always`.
Chromium headless; кожен учасник має незалежні cookies і браузерне сховище.
Фіксованих пауз немає: дії очікують потрібний видимий стан.

Після завершення сценарію всі браузерні контексти закриваються, власні
тестові записи та тимчасовий акаунт видаляються через спільний
[життєвий цикл](owned-test-data.md), зокрема якщо перевірка завершується помилкою.
Постійний пароль офіціанта не записується в trace: запис починається після входу.
Trace може містити сесійні токени, тому локальні артефакти ігноруються Git
і не призначені для публікації без перевірки.
