## Як читати таблицю

- UI — дія та результат перевіряються в браузері на справжньому сайті.
- API — запит до справжнього сервера та перевірка відповіді й збереженого стану.
- UI + API — користувацький сценарій у браузері з додатковою перевіркою стану через API.
- Дані для кожного сценарію окремі. Підготовку можна виконувати через API.
- Один ID може відповідати кільком тестовим прикладам, зокрема для різних ролей.
- Позначка «спеціальні дані» означає, що звичайних дій користувача недостатньо
  для надійного створення потрібного стану. Спосіб підготовки визначається на кроці 6.

## Узгоджені правила та межі перевірки

1. **Дві різні суми.** API списку сесій повертає суму всіх кошиків.
   Grand Total у UI — лише підтверджених. Наприклад: підтверджений кошик на $20
   і непідтверджений на $10 дають API total $30 та Grand Total $20.
2. **Останній учасник.** Власник теж є учасником, але його сесію видаляти заборонено.
   Видалення останнього гостя не обов'язково робить participants порожнім.
   Порожній список перевіряється окремо, до створення сесії власника.
3. **Повторний submit.** Очікуємо 409 без зміни вже збереженого замовлення.
4. **Не-Owner.** Інший клієнт і офіціант з валідними токенами отримують 403.
   Гостьовий токен не є токеном Cognito. Точні HTTP-коди відмови для такого
   токена та відсутнього токена перевірено на розгорнутому API на кроці 7:
   обидва отримують **401**; тест не приймає довільний код із діапазону 4xx.
5. **Повідомлення помилок.** Наведені точні тексти взято з поточного коду бекенду.
   Помилку відсутньої групи L1 перевірено на кроці 8; відмови L2 — на кроці 9.
   Для відсутнього бронювання фактичний текст — `Reservation not found.`
   Відмови L3 перевірено на кроці 10, включно з 400 для чужого учасника,
   404 для неіснуючого та 409 для Submitted/Closed.
6. **Підтверджений порожній кошик.** Звичайне підтвердження порожнього кошика
   заборонено. L2-07 потребує окремого способу підготовки: спершу перевірити,
   чи можна досягти цього стану дозволеною послідовністю API-дій; інакше
   використати контрольовану тестову фікстуру лише для власних записів.
   Підміна відповіді сервера не доводить роботу живого API.
7. **Немає Order.** Для L2-08 достатньо підтвердженого кошика гостя без створення
   власного Order. Не можна випадково порушити попередню умову й отримати
   помилку про відсутність підтверджених сесій замість перевірки Order.
8. **Чужий учасник.** Для L3-06 створюються дві незалежні групи; після відмови
   перевіряється збереження даних обох, а не тільки код відповіді.

## Загальні вимоги до виконання

| Вимога | Як підтверджуємо | Етап плану |
| --- | --- | --- |
| Позитивні й негативні сценарії кожного рівня | Сценарії з ID вище та теги рівня, UI/API й negative | 7–10 |
| Окремі тестові дані, очищення, динамічні дати | Унікальні записи на сценарій; облік створених ID; перевірка прибирання; документовані обмеження API | 6, 12 |
| Незалежність і паралельне виконання | Повторний запуск та запуск кількох сценаріїв паралельно без спільних змінюваних даних | 12 |
| Скріншоти або trace для помилок | Локальні Playwright trace для помилок перевірено; у публічному CI артефакті є безпечна категорія помилки, а сирі trace не публікуються через токени | 11–14 |
| Автоматичний запуск у CI, звіт навіть після помилки | GitHub Actions; завантаження звітів і артефактів незалежно від результату тестів; статус тестів не приховується | 13–14 |
| Інструкція для перевіряючого | [Короткий гід](reviewer-guide.md): напрям, підхід, код, запуск і звіт | 15 |
| Публічний репозиторій | Перевіряючий може відкрити код, workflow і результати без доступу до приватного репозиторію | 14–15 |

GitHub Actions уже запускає тести у хмарі. Додатковий ReportPortal не
налаштовано, тому завдання із зірочкою загалом не позначено виконаним.

Додаткове редагування страв власником, реалізоване понад BE/FE-домашку,
може отримати окремі регресійні перевірки після покриття обов'язкових вимог AQA.
